# Decisions

## 1. Requirement Understanding

The goal is to integrate Auth0 as a SAML 2.0 Identity Provider (IdP) and make our application act as the SAML Service Provider (SP).

The application must support two login flows:

1. SP-initiated: the user starts authentication from our application.
2. IdP-initiated: the user starts authentication from Auth0.

After successful authentication, the application creates a local session and exposes the authenticated user's identity.

The implementation intentionally avoids a persistent database because the assignment explicitly allows an in-memory session strategy.

---

## 2. Ambiguities and Pushback

The requirement says "customers should be able to log in" but does not define a multi-tenant customer model.

For this take-home, I assumed a single Auth0 tenant and a single SAML configuration. Multi-tenant SAML configuration is explicitly treated as out of scope.

The requirement also does not specify persistent user provisioning. I therefore treated successful SAML authentication as sufficient to establish the application session and did not introduce a user database.

For a production implementation, I would clarify:

- Whether each customer has a separate SAML connection.
- Whether users should be provisioned/JIT-created in the application.
- What application-level identifier should be used as the stable user key.
- Whether application logout must also terminate the IdP session.
- Whether sessions need to survive application restarts and horizontal scaling.

---

## 3. SAML Metadata

The backend exposes the Service Provider metadata through:

`GET /auth/saml/metadata`

The metadata is generated by `@node-saml/node-saml` rather than being maintained as a manually edited XML document.

This reduces the risk of the metadata becoming inconsistent with the application's SAML configuration.

---

## 4. Assumptions

### Identity Provider

Auth0 is treated as the trusted SAML Identity Provider.

The IdP certificate provided by Auth0 is configured through environment variables and is never committed to source control.

### User Identity

The SAML `NameID` is used as the application's external identity key.

I chose `NameID` rather than email because email addresses can change, while the IdP-provided subject identifier is intended to represent the user's identity.

The email and display name are treated as user attributes rather than the primary identity key.

### Sessions

The application uses an in-memory session store for this assignment.

Sessions are represented by a cryptographically random session ID stored in an HTTP-only cookie.

This keeps the implementation simple while demonstrating the important session lifecycle without introducing unnecessary database infrastructure.

---

## 5. SAML Validation

SAML XML signature validation is delegated to `@node-saml/node-saml` rather than implemented manually.

The backend validates the SAML response using the Auth0 IdP certificate and the configured SAML service provider settings.

The implementation also protects against assertion replay by tracking consumed assertion IDs in an in-memory store with an expiry time.

The replay store is intentionally in-memory because this is a single-instance take-home demo.

In a production deployment, replay protection would need to be shared across application instances, for example through Redis or another centralized store.

---

## 6. SP-Initiated Flow

The SP-initiated flow is:

Browser
  -> Application
  -> /auth/saml/login
  -> Auth0
  -> SAML Response
  -> /auth/saml/callback
  -> Validate assertion
  -> Create application session
  -> Redirect to frontend

The frontend then calls `/auth/me` using the session cookie and displays the authenticated identity.

---

## 7. IdP-Initiated Flow

The IdP-initiated flow is:

Browser
  -> Auth0
  -> SAML Response
  -> /auth/saml/callback
  -> Validate assertion
  -> Create application session
  -> Redirect to frontend

The same ACS endpoint is used for both flows.

The application does not rely on an SP-generated login request for the IdP-initiated flow.

Assertion replay protection remains important because an unsolicited SAML assertion must not be reusable.

---

## 8. Session and Authentication Separation

SAML authentication and application authentication are treated as separate concerns.

The SAML service is responsible for:

- Generating SP metadata
- Starting SAML authentication
- Validating SAML responses
- Extracting the authenticated identity

The session service is responsible for:

- Creating sessions
- Looking up sessions
- Expiring sessions
- Deleting sessions

Authentication middleware is responsible for checking the session before protected routes execute.

This separation keeps SAML protocol concerns independent from the application's session mechanism.

---

## 9. Logout Decision

Local application logout is implemented by deleting the server-side session and clearing the session cookie.

Full SAML Single Logout (SLO) is intentionally not implemented.

For a production implementation, logout would require a decision about whether the application or the Identity Provider is the source of truth for the user's authentication state.

A complete SLO implementation would need to consider:

- SP-initiated logout
- IdP-initiated logout
- SAML `LogoutRequest` and `LogoutResponse`
- Session indexes
- IdP availability
- Failure handling when one side cannot be reached

For this assignment, implementing local logout provides a useful demonstration without expanding the scope significantly.

---

## 10. Frontend

The frontend is intentionally minimal.

It provides:

- SP-initiated login
- IdP-initiated login
- Authenticated user information
- Local logout

Frontend visual polish is intentionally secondary because the assignment evaluates the SSO implementation and engineering decisions rather than UI styling.

---

## 11. Security and Configuration

Secrets and environment-specific configuration are kept outside source control.

The IdP certificate and Auth0 configuration are provided through environment variables and are not committed to the repository.

The session cookie is HTTP-only to prevent client-side JavaScript from directly accessing the session identifier.

The local development environment uses HTTP, so the `secure` attribute is disabled for the demo. In production it should be enabled and the application should run over HTTPS.

---

## 12. Known Limitations

The following are intentionally outside the scope of this implementation:

- Persistent session storage
- Multi-instance/shared session storage
- Shared replay protection across application instances
- Production certificate/key rotation
- Multi-tenant SAML configuration
- SCIM provisioning
- RBAC
- Production deployment
- Full SAML Single Logout

These could be added independently without changing the core SAML authentication flow.

## 13. AI Usage

AI tools were used as a development aid for:

- Reviewing implementation approaches
- Clarifying SAML and Node.js library behavior
- Troubleshooting TypeScript and library API issues
- Reviewing code structure and edge cases

The implementation and final architectural decisions were reviewed and understood manually.

No generated code was accepted without understanding how it works and why it is needed.

---

## 14. Future Production Improvements

If this were moving beyond the take-home demo, I would prioritize:

1. Shared session storage such as Redis.
2. Stronger session lifecycle and CSRF protection.
3. Production HTTPS and secure cookie configuration.
4. Centralized replay protection across instances.
5. Certificate rotation and operational monitoring.
6. SAML Single Logout.
7. Automated integration and security tests.
8. Multi-tenant SAML configuration if required by the product.
